# flake-systems-that-exist

A `forAllSystems` helper that derives the system list from what the **pinned
nixpkgs actually supports** instead of hardcoding it. A hardcoded entry the
pinned nixpkgs has since dropped is not a missing output -- it is an evaluation
**error** -- and the check you are almost certainly running cannot see it.

Verified against nixpkgs 26.11 (`nixos-unstable`, rev `f13ff45`, 2026-08) using
Nix 2.34.8. The `nix flake check` behaviour below is a property of the Nix CLI,
not of nixpkgs, so it is versioned separately.

## The problem

nixpkgs 26.11 dropped `x86_64-darwin`. The drop is a `throw`, not an omission.
`import nixpkgs { system = "x86_64-darwin"; }` fails with

```
error: Nixpkgs 26.11 has dropped support for x86_64-darwin.
```

The guard lives in `pkgs/top-level/default.nix:117-120` and fires when either
the local or the cross system is Darwin-on-x86, unless
`config.allowDeprecatedx86_64Darwin == "force"`. `lib.systems.flakeExposed` no
longer lists the system either; on this pin it is

```
x86_64-linux  aarch64-linux  armv6l-linux  armv7l-linux  i686-linux
aarch64-darwin  powerpc64le-linux  riscv64-linux  x86_64-freebsd
```

A flake's outputs are generated by mapping over a systems list -- some variant of
`genAttrs systems (system: ... import nixpkgs { inherit system; } ...)`. So a
stale entry does not make `packages.x86_64-darwin` merely absent: it makes
`packages.x86_64-darwin.<every attr>`, `devShells.x86_64-darwin.<every attr>`,
and everything else generated that way throw the moment they are forced. The
flake is broken for that platform's users in a way that looks, from their side,
like your flake does not evaluate at all.

## The standard check does not see it

`nix flake check` only evaluates outputs for systems the host can build.
Evaluated on `x86_64-linux`, the Darwin attributes are never forced:

```
$ nix flake check "path:$PWD" --no-build
evaluating flake...
checking flake output 'packages'...
checking derivation packages.x86_64-linux.default...
all checks passed!
warning: The check omitted these incompatible systems: x86_64-darwin
Use '--all-systems' to check all.
```

Exit status 0. The only signal is that closing warning on stderr, and nothing
fails on it -- a gate keyed to the exit status, which is the normal way to run
this, cannot distinguish it from a clean run. **A flake can be broken for every
macOS-on-Intel user while CI on Linux stays green indefinitely.**

Detection is one flag:

```sh
nix flake check "path:<dir>" --no-build --all-systems
```

Same flake, exit status 1:

```
checking derivation packages.x86_64-darwin.default...
error:
       … while checking flake output 'packages'
       … while checking the derivation 'packages.x86_64-darwin.default'
       error: Nixpkgs 26.11 has dropped support for x86_64-darwin.
```

Three deliberate parts to that invocation:

- `--all-systems` forces every system's outputs, not just the buildable ones.
  This is the flag that turns the warning into a failure.
- `--no-build` keeps it evaluation-only, which is sufficient: the bug is an
  evaluation error, so it surfaces the moment the attribute is forced. It is a
  speed knob, not a correctness one. Adding `--all-systems` does *not* make Nix
  attempt foreign-system builds -- with `checks.aarch64-linux.*` present on an
  `x86_64-linux` host, `nix flake check --all-systems` still reports
  `running 0 flake checks...` and exits 0. What `--no-build` drops is building
  the host's *own* `checks`, which detection does not need.
- `path:<dir>` rather than `.`, because on a git checkout `.` copies only
  **tracked** files. A systems list that has been edited into a new file but not
  yet `git add`ed makes the check fail on something else entirely, and the real
  answer never gets reached:

  ```
  error: Path 'systems.nix' in the repository "<dir>" is not tracked by Git.
  ```

  With `path:` the working tree is used as-is.

## The fix

Stop writing the list down. Intersect what you want with what the pin supports.

```nix
sys = import ./lib/flake-systems-that-exist {
  inherit (nixpkgs) lib;
  want = [ "x86_64-linux" "aarch64-linux" "aarch64-darwin" "x86_64-darwin" ];
};

packages = sys.forAllSystems (system: {
  default = (import nixpkgs { inherit system; }).hello;
});
```

Under nixpkgs 26.11 that flake passes `--all-systems`, builds three systems, and
says why the fourth is gone:

```
evaluation warning: flake-systems-that-exist: the pinned nixpkgs no longer supports x86_64-darwin; dropped from the system list. Delete the entry.
checking derivation packages.x86_64-linux.default...
checking derivation packages.aarch64-linux.default...
checking derivation packages.aarch64-darwin.default...
all checks passed!
```

Omit `want` entirely and you get every system the pin exposes -- which is the
version that can never go stale, at the cost of evaluating outputs for
`powerpc64le-linux` and friends.

## Two kinds of bad entry, treated differently

Intersection alone would swallow both. They are not the same bug.

| Entry | Example | Classified by | Result |
|-------|---------|---------------|--------|
| Dropped upstream | `"x86_64-darwin"` | parses as a system double, absent from `flakeExposed` | removed from `systems`, listed in `dropped`, warned about |
| Typo | `"x86_64-linx"` | `lib.systems.parse.mkSystemFromString` throws on it | `throw` (with `strict`, the default) |

`x86_64-darwin` still parses as a valid double in 26.11 -- the parser knows the
triple, nixpkgs just will not build for it. That difference is the only
distinguishing signal available from the pinned tree, and it is enough.

Silently dropping a typo has exactly the failure mode this recipe exists to
prevent: the flake never produces outputs for that system, and every check stays
green. Same for the degenerate case where nothing survives the intersection --
an empty system list means zero outputs and a flake that passes every check
while doing nothing, so that throws too.

## API

```nix
import ./lib/flake-systems-that-exist {
  lib,                  # from the SAME nixpkgs the outputs are built against
  want ? null,          # desired systems; null = everything the pin supports
  strict ? true,        # throw on entries that are not system doubles
  warnDropped ? true,   # warn (once, at eval) about entries the pin dropped
}
```

Returns:

```
systems         the surviving list
supported       lib.systems.flakeExposed for this pin
dropped         real doubles this pin no longer supports
typos           entries that are not doubles at all (populated regardless of
                `strict`; with strict = true it is forcing `systems` that throws)
forAllSystems   f -> lib.genAttrs systems f     (f takes the system string)
```

## Caveats

- `lib` must come from the same nixpkgs the outputs are instantiated against.
  Threading in a `lib` from a different pin reintroduces exactly the skew this
  removes, and does it invisibly.
- `flakeExposed` is descriptive, not a build guarantee. Its own header calls it
  "all system doubles for platforms where nixpkgs can do native compilation
  reasonably well". Membership means nixpkgs intends to work there; an
  individual package may still be marked unsupported or fail to build.
- This narrows the list to systems that *evaluate*. `--all-systems` is still the
  thing that proves it, and it is worth wiring into CI regardless -- a system can
  be perfectly supported and still have one of your outputs broken on it.
- `config.allowDeprecatedx86_64Darwin = "force"` suppresses that specific
  `throwIf`, but it does not buy back a working platform, and it is not an
  alternative to deleting the entry. On this pin the package set still fails to
  evaluate one layer down -- forcing so much as `pkgs.stdenv.hostPlatform.system`
  gives `Refusing to evaluate package 'libiconv-115.100.1' ... package.meta.platforms
  = [ "aarch64-darwin" ]`, and adding `allowUnsupportedSystem` only moves it to
  `Unsupported platform for the Darwin stdenv`. If you set it anyway, you are
  opting out of this recipe too -- `flakeExposed` does not know about your config.
- `warnDropped` fires on every evaluation of the flake. That is the intent (the
  entry should be deleted, not tolerated), but set it to `false` if a build log
  has to stay clean.
- Separating "dropped" from "misspelled" needs `lib.systems.parse.mkSystemFromString`,
  which is a semi-internal path. If upstream renames or moves it, `strict` mode
  breaks loudly at evaluation rather than silently. It is the only signal the
  pinned tree offers for that distinction, so the coupling is deliberate.
